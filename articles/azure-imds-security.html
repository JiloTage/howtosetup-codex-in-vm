Azure IMDSとセキュリティ

最終更新: 2026-03-26
Azure Instance Metadata Service（IMDS）の仕組みとセキュリティ上の考慮事項を解説し、SSRF攻撃の防止策やトークンキャッシュの注意点、マネージドID連携におけるベストプラクティスを示す。

Azure IMDSとセキュリティは、Azure仮想マシン上で動作するInstance Metadata Service（IMDS）のアーキテクチャと、それに関連するセキュリティリスクおよび対策を包括的に扱う記事である。IMDSはAzure マネージドIDによるトークン取得の基盤であり、オフライン環境でのCodex導入においても中核的な役割を果たす。IMDSの正しい理解と適切なセキュリティ対策は、Azure VM上でのあらゆるサービス運用において不可欠である。

IMDSとは

Azure Instance Metadata Service（IMDS）は、Azure仮想マシンの内部からのみアクセス可能なREST APIエンドポイントである。VMの構成情報、ネットワーク情報、スケジュールされたイベント、そしてマネージドIDのOAuthトークンを取得するために使用される。

169.254.169.254 エンドポイント

IMDSは、リンクローカルアドレス 169.254.169.254 で公開されている。このアドレスはAzureのハイパーバイザー層で処理され、インターネットに到達することはない。VM内部からのみアクセス可能であり、外部ネットワークからの到達は物理的に不可能な設計となっている。

# IMDSへの基本アクセス例
curl -H "Metadata: true" \
  "http://169.254.169.254/metadata/instance?api-version=2021-02-01"

主なエンドポイントは以下の通りである。

  • /metadata/instance — VM構成情報（リージョン、VMサイズ、タグ等）
  • /metadata/identity/oauth2/token — マネージドIDによるOAuthトークン取得
  • /metadata/scheduledevents — メンテナンスイベント通知
  • /metadata/attested/document — VM認証ドキュメント

Metadata: true ヘッダーの必要性

IMDSへのすべてのリクエストには、HTTPヘッダー Metadata: true を付与する必要がある。このヘッダーが欠落したリクエストはIMDSにより拒否される。これはSSRF（Server-Side Request Forgery）攻撃を防止するための重要なセキュリティメカニズムである。

ウェブアプリケーションの脆弱性を通じて攻撃者がサーバーから任意のHTTPリクエストを発行させた場合でも、通常のブラウザやHTTPクライアントライブラリは Metadata: true ヘッダーを自動的に付加しない。このため、SSRF経由でのIMDSアクセスが困難になる。ただし、これは多層防御の一環であり、単独では完全な防御とはならない。

SSRF攻撃ベクトルと防止策

SSRF（Server-Side Request Forgery）は、攻撃者がサーバーサイドのアプリケーションを悪用して、本来アクセスできない内部リソースへリクエストを送信させる攻撃手法である。クラウド環境におけるIMDSは、SSRFの主要なターゲットとなる。

代表的な攻撃シナリオ

以下のようなシナリオでIMDSが標的となり得る。

  1. Webアプリケーション経由: URLパラメータを受け取るWebアプリに http://169.254.169.254/... を注入し、IMDSからトークンを窃取する
  2. HTTPリダイレクト悪用: 外部URLへのリクエストを途中でIMDSにリダイレクトさせる
  3. DNSリバインディング: DNS応答を操作し、正規ドメインの解決先をIMDSのIPアドレスに変更する
  4. ヘッダーインジェクション: HTTPヘッダーインジェクションにより Metadata: true ヘッダーを付加させる

防止策

SSRF対策としては以下の多層防御が重要である。

  • ネットワークレベルの制御: Azure NSG（ネットワークセキュリティグループ）を活用し、VM内の不要なアウトバウンド通信を制限する
  • アプリケーションレベルの対策: ユーザー入力のURL検証を厳格に行い、リンクローカルアドレス（169.254.0.0/16）へのリクエストをブロックする
  • WAF（Web Application Firewall）: Azure Application GatewayのWAF機能でSSRFパターンを検知・遮断する
  • 最小権限の原則: マネージドIDに付与するロールを必要最小限に絞る（例: 「Cognitive Services OpenAI User」のみ）
  • IMDSv2の活用: セッションベースのトークンを使用するIMDSv2を有効化し、単純なGETリクエストでのトークン取得を防止する

トークンキャッシュの考慮事項

IMDSから取得したOAuthトークンには有効期限（通常は数時間）が設定されている。トークンの取り扱いにおいて以下の点に注意する必要がある。

キャッシュのメリット

  • IMDSへの頻繁なリクエストを避け、レートリミットの回避およびレイテンシの低減が可能
  • トークン取得のオーバーヘッドを削減し、アプリケーションの応答性が向上する

キャッシュのリスク

  • メモリ上のトークン露出: プロセスメモリダンプやコアダンプからトークンが漏洩するリスクがある。環境変数に設定したトークンは /proc/<pid>/environ 経由で読み取られる可能性がある
  • ファイルへのキャッシュ禁止: トークンをディスク上のファイルにキャッシュすることは強く推奨されない。他のプロセスやユーザーからアクセスされるリスクがある
  • 有効期限の管理: トークンの expires_on フィールドを監視し、有効期限が近づいたら再取得する仕組みを実装する

Codex導入ガイドで紹介されている .bashrc 関数方式では、codexコマンドの実行ごとにトークンを取得するため、キャッシュに起因するリスクは最小限に抑えられている。

--noproxy フラグの重要性

企業のAzure VM環境では、HTTP/HTTPSプロキシが設定されていることが多い。http_proxy や https_proxy 環境変数が設定されている場合、curlはデフォルトでプロキシ経由で通信を行う。しかし、IMDSのリンクローカルアドレス（169.254.169.254）はプロキシ経由で到達できないため、アクセスが失敗する。

# プロキシ環境下でのIMDSアクセス（失敗する例）
curl -H "Metadata: true" \
  "http://169.254.169.254/metadata/identity/oauth2/token?api-version=2018-02-01&resource=https://cognitiveservices.azure.com"

# --noproxy フラグを使用（正しい方法）
curl --noproxy "*" -H "Metadata: true" \
  "http://169.254.169.254/metadata/identity/oauth2/token?api-version=2018-02-01&resource=https://cognitiveservices.azure.com"

恒久的な対策として、no_proxy 環境変数にIMDSアドレスを追加しておくことが推奨される。

# .bashrc に追記
export no_proxy="169.254.169.254,$no_proxy"

Azure SDKを使用する場合も同様に、HTTPクライアントの設定でプロキシ除外を明示的に指定する必要がある。Codex CLIやその他のNode.jsベースのツールでは、NO_PROXY 環境変数がHTTPライブラリに参照される。

IMDSとマネージドIDの関係

Azure マネージドIDは、Azure リソースに対して自動的に管理されるIDを提供する機能であり、IMDSはそのトークン取得メカニズムの基盤として機能する。

トークン取得フロー

  1. VM内のアプリケーションがIMDSの /metadata/identity/oauth2/token エンドポイントにリクエストを送信
  2. IMDSはAzureファブリックコントローラーを通じてMicrosoft Entra ID（旧Azure AD）にトークンを要求
  3. Microsoft Entra IDがマネージドIDの資格情報を検証し、OAuthトークンを発行
  4. IMDSがトークンをVM内のアプリケーションに返却

この仕組みにより、アプリケーションはシークレットやAPIキーを保持する必要がなく、VMのセキュリティが大幅に向上する。SCPでオフラインVM にソフトウェアを配布する場合にも、認証情報の転送が不要となる利点がある。

システム割り当てとユーザー割り当て

  • システム割り当てマネージドID: VMのライフサイクルに紐付く。VMを削除するとIDも自動削除される。1つのVMに1つのみ
  • ユーザー割り当てマネージドID: 独立したAzureリソースとして作成。複数のVMで共有可能。VMを削除してもIDは残る

ユーザー割り当てマネージドIDを使用する場合、IMDSへのトークンリクエストに client_id パラメータを追加する必要がある。

# ユーザー割り当てマネージドIDの場合
curl --noproxy "*" -fsS -H "Metadata: true" \
  "http://169.254.169.254/metadata/identity/oauth2/token?api-version=2018-02-01&resource=https://cognitiveservices.azure.com&client_id=<USER_ASSIGNED_CLIENT_ID>"

セキュリティベストプラクティス

Azure VMでIMDSおよびマネージドIDを安全に運用するための推奨事項を以下にまとめる。

  1. 最小権限の原則を徹底する: マネージドIDに付与するRBACロールは必要最小限とする。「所有者」や「共同作成者」などの広範なロールは避ける
  2. ネットワークセキュリティを強化する: NSGルールでVM からのアウトバウンド通信を必要なエンドポイントのみに制限する
  3. アプリケーションの入力検証を厳格にする: ユーザー入力に基づくHTTPリクエストを行う場合、宛先IPアドレスを検証しリンクローカルアドレスへのアクセスを禁止する
  4. トークンのライフサイクルを管理する: トークンは必要な時に取得し、メモリ上でのみ保持し、不要になったら速やかに破棄する
  5. IMDSアクセスログを監視する: Azure Monitorと連携してIMDSへの異常なアクセスパターンを検知する
  6. iptablesでIMDSアクセスを制限する: VM内で特定のユーザー／プロセスのみがIMDSにアクセスできるようiptablesルールを設定する
  7. no_proxy を適切に設定する: プロキシ環境下でのIMDSアクセス問題を防止する
  8. 定期的なセキュリティレビュー: Azure VMのセキュリティベストプラクティスに沿って定期的に構成を見直す
