Azure マネージドID

最終更新: 2026-03-26
Azure マネージドIDは、Azure リソースが資格情報を管理せずに Azure AD トークンを取得するための仕組みであり、シークレットレスな認証を実現する。本記事ではシステム割り当てとユーザー割り当ての違い、IMDS経由のトークン取得フロー、RBAC連携、Azure OpenAI での活用、およびセキュリティ上のベストプラクティスを解説する。

Azure マネージドID（Managed Identity）は、Azure Active Directory（Azure AD）が提供する機能であり、Azure 上のリソースがパスワードやシークレットを保持することなく、他の Azure サービスへ安全に認証するための仕組みである。従来はサービスプリンシパルのクライアントシークレットや証明書を手動で管理する必要があったが、マネージドIDを利用することでこれらの資格情報管理が不要になる。Azure VMへのCodex導入ガイド（オフライン環境）においても、VM から Azure OpenAI API へアクセスする際にマネージドIDを使った認証が推奨される。

概要と基本概念

マネージドIDは Azure AD のサービスプリンシパルの一種であるが、ライフサイクルが Azure リソースに紐づいている点が大きな特徴である。リソースが削除されると対応するマネージドIDも自動的に削除され、孤立した資格情報が残るリスクがない。

マネージドIDの根幹にあるのは、Azure のインフラストラクチャが自動的にトークンの発行・ローテーションを行うという点である。開発者やオペレーターがシークレットの有効期限を管理したり、ローテーションスクリプトを書いたりする必要がなくなる。これにより、Azure AD 認証のベストプラクティスに沿ったセキュアな運用が容易になる。

システム割り当てとユーザー割り当て

システム割り当てマネージドID

システム割り当て（System-assigned）マネージドIDは、Azure リソース（VM、App Service、Functions など）を作成する際に直接有効化する。このIDは当該リソースと1対1で紐づき、リソースの削除時に自動的に削除される。設定が簡単であり、単一リソースが少数のサービスにアクセスする場合に適している。

ユーザー割り当てマネージドID

ユーザー割り当て（User-assigned）マネージドIDは、独立した Azure リソースとして作成され、複数の Azure リソースに関連付けることができる。例えば、複数の VM が同一の Azure Key Vault や Azure OpenAI リソースにアクセスする場合、1つのユーザー割り当てIDを共有することでRBAC（ロールベースアクセス制御）の管理が簡素化される。リソースの削除時にIDは残存するため、ライフサイクルを独立して管理できる。

特性 システム割り当て ユーザー割り当て
ライフサイクル リソースと連動 独立管理
共有 不可（1対1） 複数リソースで共有可
作成方法 リソース設定で有効化 独立リソースとして作成
適用シナリオ 単一リソースの単純なアクセス 複数リソースの統一アクセス管理

IMDS によるトークン取得フロー

マネージドIDのトークン取得は、Azure Instance Metadata Service（IMDS）を介して行われる。IMDS は VM 内部からのみアクセス可能なリンクローカルアドレス（169.254.169.254）で動作し、外部ネットワークからのアクセスは不可能である。

トークン取得の手順

アプリケーションは以下のエンドポイントに HTTP GET リクエストを送信してトークンを取得する：

GET http://169.254.169.254/metadata/identity/oauth2/token
  ?api-version=2018-02-01
  &resource=https://cognitiveservices.azure.com/
Header: Metadata: true

レスポンスにはアクセストークン（JWT）、有効期限、リソース情報が含まれる。取得したトークンは Azure OpenAI を含む対象リソースの API 呼び出し時に Bearer トークンとして使用する。

トークンにはキャッシュの有効期限（通常1時間）が含まれており、SDK（Azure Identity ライブラリ）を使用する場合は自動的にキャッシュとリフレッシュが行われる。手動実装の場合は expires_on フィールドを確認し、期限切れ前に再取得する処理を実装する必要がある。

ロールの割り当て（RBAC）

マネージドIDにアクセス権限を付与するには、Azure RBAC でロールを割り当てる。マネージドIDはサービスプリンシパルとして扱われるため、通常のユーザーやグループと同様にロール割り当てが可能である。

主なロール割り当て例

  • Cognitive Services OpenAI User - Azure OpenAI リソースへの推論リクエスト実行
  • Key Vault Secrets User - Azure Key Vault からのシークレット読み取り
  • Storage Blob Data Reader - Azure Blob Storage からのデータ読み取り
  • Contributor - リソースグループ内の管理操作（必要最小限に制限すべき）

最小権限の原則に従い、必要なリソースに対して必要最小限のロールのみを付与することが重要である。スコープはリソースグループ単位ではなく個別リソース単位に絞ることが推奨される。

Azure OpenAI での活用

マネージドIDは、Codex や Azure OpenAI Service と組み合わせて使用する場合に特に有用である。API キーをコードや設定ファイルに埋め込む代わりに、マネージドIDを使った Azure AD 認証でトークンを取得し、API リクエストに使用する。

設定手順

  1. VM のシステム割り当てマネージドIDを有効化する
  2. Azure OpenAI リソースに対して Cognitive Services OpenAI User ロールを割り当てる
  3. アプリケーションコードで Azure Identity SDK を使用してトークンを取得する
  4. 取得したトークンを Authorization: Bearer ヘッダーに設定して API を呼び出す

オフライン環境においては、SCP によるファイル転送でアプリケーションパッケージを配置し、Node.js のオフラインインストール後にマネージドIDを用いた認証を設定する流れとなる。VM が Azure AD エンドポイントに到達できる限り、インターネットへの完全な接続は不要である。

セキュリティ上の利点

マネージドIDを使用することで、以下のセキュリティリスクを軽減できる：

  • シークレット漏洩の防止 - コードリポジトリ、環境変数、構成ファイルにシークレットが存在しないため、漏洩のリスクがゼロになる
  • 資格情報ローテーションの自動化 - Azure プラットフォームが内部的にトークンのローテーションを管理するため、手動のローテーション運用が不要
  • 最小権限の原則 - RBAC を通じて細かいスコープでのアクセス制御が可能
  • 監査性 - Azure AD のサインインログにマネージドIDのトークン取得が記録され、監査証跡が残る
  • IMDS のセキュリティ - IMDS のセキュリティにより、トークンエンドポイントへのアクセスは VM 内部に限定される

ベストプラクティス

ID の種類の選択

単一リソースで完結する場合はシステム割り当て、複数リソースで共有する場合はユーザー割り当てを選択する。迷った場合は、ユーザー割り当ての方が柔軟性が高く、将来の拡張に対応しやすい。

スコープの最小化

ロール割り当てのスコープは可能な限り狭くする。サブスクリプション全体ではなく、リソースグループまたは個別リソースに対して割り当てることが望ましい。

SDK の使用

Azure Identity SDK（DefaultAzureCredential）を使用することで、トークンのキャッシュ・リフレッシュ・フォールバックが自動化される。IMDS エンドポイントへの直接アクセスは、SDK が利用できない環境でのみ検討する。

モニタリングとアラート

Azure AD のサインインログとアクティビティログを定期的に監視し、意図しないトークン取得やロール変更を検知するアラートを設定する。Azure AD 認証の監視体制を整備することが推奨される。
